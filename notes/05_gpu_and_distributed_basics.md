# GPU原理与分布式训练基础

## 1. 深度学习计算与扩展背景
* **计算资源与扩展定律 (Scaling Laws)**: 语言模型的性能强依赖于计算资源的扩展。无论是预训练还是推理阶段，更多的计算资源（通过处理更多数据、训练更大模型）能直接带来性能提升。
* **硬件性能转换**: 
  * **Dennard 缩放定律 (Dennard Scaling) 与摩尔定律的停滞**: 早期通过微缩晶体管提升时钟频率且降低功耗的 Dennard 缩放定律在 2004 年左右失效。单线程 CPU 性能增长平缓，促使计算加速走向并行扩展。
  * **并行扩展**: 深度学习的本质是将单线程的绝对速度提升，转变为大规模并行计算的吞吐量提升。从早期 GPU（如 K20）到现代加速器（如 H100、B200），GPU 的算力呈超级指数级增长，如何高效利用这些算力成为大模型训练的核心。

## 2. GPU 硬件架构入门基础课 (Intro to GPU Hardware)

### 2.1 SM (流式多处理器) 与 CUDA Core (SP, 流式处理器)
要理解 GPU 的运行机制，首先需要理清其物理芯片上的核心计算单元：
* **流式多处理器 (SM, Streaming Multiprocessor)**: 
  * **定义**: SM 是 GPU 的大局控制与物理执行的基本单元，类似于 CPU 中的“核心（Core）”，但其设计要庞大得多。
  * **内部组成**: 每个 SM 内部包含自己独立的 **Warp 调度器 (Warp Scheduler)**、**指令缓存 (Instruction Cache)**、**寄存器堆 (Register File)**、**片上共享内存 (Shared Memory / L1 Cache)**，以及成百上千个用于执行算术运算的底层计算单元（如 CUDA Cores 和 Tensor Cores）。
  * **调度机制**: GPU 的硬件调度器以 **线程束 (Warp)** 为最小调度单位，一个 Warp 包含 32 个物理线程。同一个 Warp 中的所有线程在同一时刻只能执行相同的指令，但处理不同的数据，这种执行模式被称为 **SIMT (单指令多线程, Single Instruction Multiple Threads)**。
* **流式处理器 (SP, Streaming Processor / CUDA Core)**:
  * **定义**: SP 是 SM 内部最基础的、负责执行单条基本指令（如加法、乘法等）的物理算术逻辑单元 (ALU)。
  * **与 Tensor Core 的区别**: CUDA Core (SP) 擅长处理一维的标量或向量运算；而现代 GPU 引入的 **张量核心 (Tensor Core)** 则是专门特化于矩阵乘法 (GEMM) 与累加（$D = A \times B + C$）的超大硬件单元，能在一个时钟周期内完成巨大的矩阵相乘，是大模型计算的算力主力。

### 2.2 寄存器 vs 共享内存 (SRAM) vs HBM (DRAM) 内存层次结构与书桌类比
GPU 的存储结构分为多个层级。离计算单元（ALU）越近，访问速度（延迟）越快，但物理容量越小。为了形象地理解这一层次，我们可以使用一个 **“书桌/抽屉/文件柜”** 的类比：

![GPU 底层存储层次结构书桌类比](images/gpu_memory_hierarchy_analogy.drawio.png)

1. **寄存器 (Registers)**:
   * **类比**: **你手头正在读写的纸张，或者你正握在手中的笔**。
   * **特点**: 物理上直接位于 SM 的算术单元旁边。每个线程拥有自己专属的寄存器。这是 GPU 上速度最快、延迟最低的存储媒介。
   * **性能与大小**: 访问延迟几乎为 **0 到 1 个时钟周期**（小于 1 ns）。但容量极其珍贵，每个 SM 的寄存器堆总量通常只有 64KB 至 256KB，分配到每个线程手里仅能存几十个 float 数据。
2. **共享内存 (Shared Memory / SRAM)**:
   * **类比**: **书桌的抽屉 (Desk Drawer)**。
   * **特点**: 物理上位于 SM 内部。属于同一个线程块 (Block) 内的所有线程共享这一块内存。如果多个线程需要协同工作、重用相同的数据，可以先把数据搬到共享内存中，类似于坐在同一张桌子前的组员共同查看抽屉里的参考书。
   * **性能与大小**: 访问延迟约为 **20 到 30 个时钟周期**（十几 ns）。容量通常为每个 SM 96KB 到 228KB。
3. **全局内存/显存 (Global Memory / HBM / DRAM)**:
   * **类比**: **走廊尽头的庞大文件柜 (Filing Cabinet)**。
   * **特点**: 物理上位于 GPU 芯片外部（片外），如高带宽显存 HBM（High Bandwidth Memory）或传统的 GDDR 显存。所有的 SM、所有的线程块都可以访问全局内存，但必须通过总线进行跨芯片读取。
   * **性能与大小**: 访问延迟极大，通常需要 **200 到 300 个时钟周期**（甚至高达数百 ns）。尽管速度慢，但其容量巨大，目前现代 GPU（如 H100、A100）的 HBM 容量可达 80GB 到 96GB。

**GPU 存储层级对比表**:

| 存储介质 | 物理位置 | 访问延迟 (时钟周期) | 典型容量 | 共享范围 |
| :--- | :--- | :--- | :--- | :--- |
| **寄存器 (Registers)** | SM 内部 | 0 - 1 | 每个线程极小 (数 KB) | 仅单线程私有 |
| **共享内存 (Shared Memory)** | SM 内部 | 20 - 30 | 每个 SM 约 96 - 228 KB | 线程块 (Block) 内共享 |
| **L2 缓存 (L2 Cache)** | 片上 (On-Chip) | 100 左右 | 几十 MB | 整个 GPU 所有 SM 共享 |
| **全局内存 (HBM/DRAM)** | 片外 (Off-Chip) | 200 - 300 | 80 - 96 GB | 整个 GPU 所有 SM 共享 |

### 2.3 内存带宽 (Memory Bandwidth) vs 计算吞吐量 (Computation Capacity)
在大模型优化中，经常提到这两个核心指标：
* **计算吞吐量 (Computation Capacity / Peak FLOPs)**:
  * **定义**: 指 GPU 计算核心（主要是 Tensor Cores）在单位时间内能够执行的最大浮点运算次数。通常以 TFLOPs（每秒万亿次浮点运算）衡量。
  * **例如**: NVIDIA H100 GPU 的 FP16 矩阵计算吞吐量高达 **1513 TFLOPs**。
* **内存带宽 (Memory Bandwidth)**:
  * **定义**: 指数据从片外全局内存 (HBM/DRAM) 传输到片上 SRAM (共享内存/寄存器) 的最大速率。以 GB/s 或 TB/s 衡量。
  * **例如**: NVIDIA H100 GPU 的 HBM3 带宽约为 **3.35 TB/s**。
* **非对称增长 (Asymmetric Growth)**:
  在过去的几代 GPU 演进中，**计算吞吐量增长了成千上万倍，而内存带宽仅增长了数十倍**。这导致了“内存墙（Memory Wall）”问题：GPU 的计算速度极快，但数据输入的速度无法跟上，导致大量算子因为“等数据”而让计算核心处于空闲状态。

## 3. 屋顶线模型 (Roofline Model) 与算子瓶颈分析

屋顶线模型是一个用于定量评估算子瓶颈的直观模型。它将算子限制分为两个区域：**内存带宽受限 (Memory-bound)** 和 **计算受限 (Compute-bound)**。

### 3.1 算术强度 (Arithmetic Intensity) 的定义
要判断一个算子处于哪种受限状态，首先需要计算其 **算术强度 (Arithmetic Intensity)**，其定义为：
$$I = \frac{\text{计算量 (FLOPs)}}{\text{内存访问量 (Bytes)}}$$
* **计算量 (FLOPs)**: 算子执行的浮点运算总次数。
* **内存访问量 (Bytes)**: 算子从 HBM 读取的数据量与写入 HBM 的数据量之和。

**硬件临界算术强度 (Knee Point / 拐点)**:
每个 GPU 硬件都有一个特有的临界值 $I_{knee}$，计算公式为：
$$I_{knee} = \frac{\text{硬件计算吞吐量 (FLOPs/s)}}{\text{硬件内存带宽 (Bytes/s)}}$$
* **H100 PCIe 实例**: FP16 吞吐为 $1513 \text{ TFLOPs}$，HBM 带宽为 $3.35 \text{ TB/s}$。
  $$I_{knee} = \frac{1513 \times 10^{12} \text{ FLOPs}}{3.35 \times 10^{12} \text{ Bytes}} \approx 451.6 \text{ FLOPs/Byte}$$
* **结论**: 对于 H100 而言，如果一个算子每传输 1 字节的数据，未能执行至少约 452 次浮点计算，那么该算子就必定属于 **Memory-bound (内存受限)**；反之，若大于该值，则是 **Compute-bound (计算受限)**。

---

### 3.2 内存受限 (Memory-bound) 算子与实例
* **特点**: 算术强度 $I < I_{knee}$。限制算子运行时间的是数据在 HBM 和片上之间的搬运速度，而非计算核心的算力。
* **典型算子**: LayerNorm、RMSNorm、Softmax、Activation（如 ReLU, GELU）、Element-wise Add 等。

#### 实例分析：逐元素加法 (Element-wise Add)
考虑对两个 FP32 类型（每个元素 4 字节）的向量进行加法：$y_i = x_i + z_i$，长度为 $N$。
1. **计算量 (FLOPs)**: $N$ 次浮点加法，总计 $N$ FLOPs。
2. **内存访问量 (Bytes)**:
   * 从 HBM 读取向量 $x$: $4N$ 字节
   * 从 HBM 读取向量 $z$: $4N$ 字节
   * 将结果 $y$ 写回 HBM: $4N$ 字节
   * 总访存量 = $12N$ 字节。
3. **算术强度**:
   $$I = \frac{N \text{ FLOPs}}{12N \text{ Bytes}} \approx 0.083 \text{ FLOPs/Byte}$$
4. **瓶颈分析**: $0.083 \ll 451.6$。在 H100 上，该算子的实际性能将远远落后于峰值算力，GPU 大约有 99.9% 的时间都在等待数据搬运。

---

### 3.3 计算受限 (Compute-bound) 算子与实例
* **特点**: 算术强度 $I \ge I_{knee}$。计算核心被完全占满，性能达到了硬件的算力上限。
* **典型算子**: 大矩阵乘法 (GEMM)、通道数很大的卷积 (Convolution)。

#### 实例分析：矩阵乘法 (Matrix Multiplication)
考虑两个矩阵相乘：$C = A \times B$，其中 $A \in \mathbb{R}^{M \times K}$，$B \in \mathbb{R}^{K \times N}$，计算得到 $C \in \mathbb{R}^{M \times N}$。数据类型为 FP16（每个元素 2 字节）。
1. **计算量 (FLOPs)**: 矩阵中每个元素需要进行 $K$ 次乘法和 $K$ 次加法，总计 $2MNK$ FLOPs。
2. **内存访问量 (Bytes) - 朴素实现**:
   若每次计算都从 HBM 直接读取元素，其访存开销极其巨大。
3. **内存访问量 (Bytes) - 分块 (Tiling) 实现**:
   * 在实际计算中，我们通过片上共享内存（SRAM）进行**分块复用**。
   * 将大矩阵切分为大小为 $B_M \times B_K$ 和 $B_K \times B_N$ 的小图块（Tile）载入共享内存中，在 SRAM 内部执行局部矩阵乘法并累加。
   * 优化后的 HBM 访存量可以降低为：$2 \times (MK + KN + MN)$ 字节（只需将 $A, B$ 载入一次，并写回结果 $C$）。
4. **算术强度 (当 $M=N=K$ 且矩阵足够大时)**:
   * 计算量 = $2N^3$ FLOPs
   * 访存量 = $6N^2$ Bytes
   * 算术强度:
     $$I = \frac{2N^3}{6N^2} = \frac{N}{3} \text{ FLOPs/Byte}$$
   * **瓶颈分析**: 当 $N$ 足够大（例如 $N > 1500$）时，算术强度将远远超过 H100 的临界值 $451.6$，因此大矩阵乘法能够充分压榨出 GPU 的巅峰算力，属于典型的 **Compute-bound** 算子。

## 4. GPU 核心优化技术

### 4.1 避免 Warp 内条件分支分化 (Branch Divergence)
* **原理**: SIMT 模式下，同一个 Warp 内的 32 个线程必须在同一时刻执行相同的物理指令。
* **分化开销**: 若代码包含条件分支（如 `if (threadIdx.x < 16)`），Warp 内的部分线程走 `if` 分支，另一部分走 `else` 分支。此时，GPU 无法并行执行两个分支，而是让不满足条件的线程休眠，串行依次执行 `if` 和 `else`。这会导致硬件利用率直接折半。
* **优化策略**: 在编写底层 Kernel 时，尽量避免在 Warp 内部设计非对齐的条件判断，或者通过数学公式消除 `if-else`。

### 4.2 低精度计算与混合精度训练 (Mixed Precision)
* **原理**: 减少数据位数（如从 FP32 到 FP16/BF16，甚至 INT8/FP4）可以成倍降低全局内存读写开销。例如，从 FP32 降低到 FP16 意味着在相同的内存带宽下，可以获得 2 倍的内存传输吞吐量。
* **混合精度矩阵乘法**:
  * 输入使用 16 位低精度（FP16/BF16）载入；
  * 在张量核心（Tensor Core）中以 32 位精度进行乘法累加（保存部分和以维持高精度与数值稳定）；
  * 输出时将结果向下转换为 16 位写回内存。

### 4.3 算子融合 (Kernel Fusion)
* **未融合状态 (流水线搬运开销)**:
  对输入执行 $y = \text{GELU}(\text{LayerNorm}(x))$，在 PyTorch 中默认会先启动一个 LayerNorm Kernel，将中间结果写回 HBM，再启动一个 GELU Kernel 从 HBM 读取并计算。这引入了多次昂贵的片外显存往返。
* **融合状态**:
  编写一个单一的 Kernel，让线程从 HBM 中读取 $x$ 后，在片上寄存器/共享内存中连续计算完 LayerNorm 和 GELU，最后只把最终结果 $y$ 写回 HBM。大幅减少了 HBM 读写开销。

### 4.4 内存合并 (Memory Coalescing) 与突发模式
* **突发模式 (Burst Mode)**: 硬件访问片外 DRAM/HBM 时，存在高额的建立连接与寻址延迟。为了掩盖开销，DRAM 每次访问并非仅返回单字节，而是连续返回一整段相邻的物理内存块（突发段）。
* **内存合并**: 当一个 Warp 中的 32 个线程在同一时刻发起内存请求时，如果它们访问的物理内存地址是**连续对齐**的，硬件会将这些请求合并为一次 DRAM 突发读取；若访问地址杂乱离散，则会触发 32 次独立的突发读取，导致带宽浪费 32 倍。
* **矩阵访问优化**:
  * 线程应该按行方向在列上递增访问连续地址（对于行优先存储的矩阵），从而合并内存请求；避免让相邻线程访问矩阵的不同行（地址跨度极远，无法合并）。
  * **零填充 (Padding)**: 在矩阵每一行末尾填充无用零元素，使得每一行的首地址与 DRAM 突发段的边界对齐，确保首列的读取也能合并。

### 4.5 矩阵分块 (Tiling) 与波形量化 (Wavefront Quantization)
* **分块 (Tiling)**: 
  * *问题*: 朴素的矩阵相乘中，每个数据元素会被重复读取 $N$ 次，造成巨大的全局内存瓶颈。
  * *方案*: 将大矩阵划分为尺寸为 $t \times t$ 的小图块（Tile）。一次性将图块载入到 SM 的共享内存（SRAM）中，然后在高速共享内存中完成小图块之间的内积计算与累加，完成后移向下一块。
  * *效果*: 全局内存读取次数降低为原来的 $1/t$ 倍。
* **局限性与权衡**: 图块尺寸 $t$ 不能太大，否则会超出共享内存的物理容量上限。
* **波形量化 (Wavefront/Quantization Cliffs)**:
  * 图块尺寸若选择不当，会导致矩阵划分的 Tile 总数无法被 SM 的可用物理数量整除。
  * 例如：A100 包含 108 个物理 SM。若划分出 98 个 Tile，可一波全部在 SM 上并行运行；若将矩阵稍微变大，导致 Tile 数增加到 120 个，则需要两波（Wave）调度：第一波运行 108 个，第二波仅运行 12 个，其余 96 个 SM 处于空闲等待状态，这会导致整体计算效率骤降（“量子悬崖”现象）。
  * **Andrej Karpathy 案例**: 在 nanoGPT 中，通过将词表大小从 50257 增大到 50304（64的倍数），通过适当填充增加了几十个维度，反而使得瓦片对齐更加完美，带来 25% 的端到端训练加速。

## 5. 综合实践案例：FlashAttention 与在线 Softmax

经典注意力机制（Naive Attention）的计算公式为：
$$S = Q K^T \in \mathbb{R}^{N \times N}, \quad P = \text{softmax}(S) \in \mathbb{R}^{N \times N}, \quad O = P V \in \mathbb{R}^{N \times d}$$
其中 $N$ 为序列长度，$d$ 为 Head 维度。
在朴素计算中，我们需要在 HBM 中写入并多次读取大小为 $N \times N$ 的中间注意力矩阵 $S$ 和 $P$，在长文本场景下（$N$ 很大），这会造成严重的 **Memory-bound** 瓶颈，并导致显存爆炸。

### 5.1 经典 Softmax 的两遍扫描 (Classic 2-pass Softmax) 瓶颈
对于包含元素 $[x_1, x_2, \dots, x_N]$ 的向量 $\mathbf{x}$，为了防止指数计算溢出，经典的数值安全 Softmax 计算流程如下：
1. **Pass 1 (求最大值)**:
   $$m = \max_{1 \le i \le N} x_i$$
2. **Pass 2 (求指数和与归一化)**:
   先求分母累加和：
   $$d = \sum_{i=1}^N e^{x_i - m}$$
   再计算最终输出：
   $$a_i = \frac{e^{x_i - m}}{d}$$
* **HBM 读写瓶颈**:
  在硬件执行时，由于最大值 $m$ 需要汇总整行所有元素才能得到，所以在 $m$ 计算出来之前，我们无法计算任何一个指数项 $e^{x_i - m}$。这导致：
  1. 我们必须先将整个向量 $\mathbf{x}$ 从 HBM 载入片上，计算出 $m$。
  2. 随后，我们必须再次将整个向量 $\mathbf{x}$ 从 HBM 中载入，结合刚才算出的 $m$ 计算指数和 $d$。
  3. 最后，我们还要将这些值进行归一化计算，并把结果 $a_i$ 写回 HBM。
  4. 如果这中间涉及到大矩阵，我们就需要在 HBM 中来回读写多次，产生了极大的显存带宽开销。

---

### 5.2 在线 Softmax (Online Softmax) 的数学推导
为了避免对数据的多次全局内存读取，在线 Softmax（Online Softmax）允许我们在数据被逐块（Tile）载入片上内存（SRAM/寄存器）的过程中，**以增量递推的方式动态更新最大值与指数和**，从而实现只需“一次扫描（1-pass）”便可完成 Softmax 计算。

#### 递推公式推导
假设我们将输入向量 $\mathbf{x}$ 划分为若干个局部子块。现考虑前两块的合并过程：
设第一部分为 $\mathbf{x}^{(1)} = [x_1, \dots, x_k]$，第二部分为 $\mathbf{x}^{(2)} = [x_{k+1}, \dots, x_{k+p}]$。

1. **第一部分的局部统计量**:
   * 局部最大值：
     $$m^{(1)} = \max_{1 \le i \le k} x_i$$
   * 局部归一化指数和（以 $m^{(1)}$ 为基准）：
     $$d^{(1)} = \sum_{i=1}^k e^{x_i - m^{(1)}}$$

2. **第二部分的局部统计量**:
   * 局部最大值：
     $$\tilde{m} = \max_{k+1 \le i \le k+p} x_i$$
   * 局部归一化指数和（以 $\tilde{m}$ 为基准）：
     $$\tilde{d} = \sum_{i=k+1}^{k+p} e^{x_i - \tilde{m}}$$

3. **合并两部分后的全局统计量**:
   我们希望计算合并后的全局最大值 $m^{(2)}$ 和以 $m^{(2)}$ 为基准的全局归一化指数和 $d^{(2)}$：
   * 全局最大值显然为：
     $$m^{(2)} = \max(m^{(1)}, \tilde{m})$$
   * 全局归一化指数和定义为：
     $$d^{(2)} = \sum_{i=1}^{k+p} e^{x_i - m^{(2)}} = \sum_{i=1}^k e^{x_i - m^{(2)}} + \sum_{i=k+1}^{k+p} e^{x_i - m^{(2)}}$$

4. **将 $d^{(2)}$ 转化为由已知的 $d^{(1)}$ 和 $\tilde{d}$ 表达的形式**:
   * 展开第一项：
     $$\sum_{i=1}^k e^{x_i - m^{(2)}} = \sum_{i=1}^k e^{x_i - m^{(1)} + m^{(1)} - m^{(2)}} = e^{m^{(1)} - m^{(2)}} \sum_{i=1}^k e^{x_i - m^{(1)}} = d^{(1)} e^{m^{(1)} - m^{(2)}}$$
   * 展开第二项：
     $$\sum_{i=k+1}^{k+p} e^{x_i - m^{(2)}} = \sum_{i=k+1}^{k+p} e^{x_i - \tilde{m} + \tilde{m} - m^{(2)}} = e^{\tilde{m} - m^{(2)}} \sum_{i=k+1}^{k+p} e^{x_i - \tilde{m}} = \tilde{d} e^{\tilde{m} - m^{(2)}}$$
   * 合并两项，得到 **在线 Softmax 增量更新公式**:
     $$d^{(2)} = d^{(1)} e^{m^{(1)} - m^{(2)}} + \tilde{d} e^{\tilde{m} - m^{(2)}}$$

#### 硬件执行优势
有了上述公式，GPU 线程块在处理一行数据时，可以采取如下流程：
1. **分块加载 (Tiling)**: 从 HBM 中读取一小块数据 $\mathbf{x}^{(j)}$ 到片上 SRAM/寄存器。
2. **片上动态更新**: 计算该小块的局部最大值 $\tilde{m}$ 和局部和 $\tilde{d}$，利用增量公式更新保存在寄存器中的全局最大值 $m^{(j)}$ 和全局和 $d^{(j)}$。
3. **输出缩放**: 在整行扫描完毕后，我们手中已有了最终的全局最大值 $m$ 和全局指数和 $d$。此时，我们只需对之前保存在寄存器中的中间乘积结果，统一乘以缩放因子 $e^{m^{(j)} - m}$ 并除以 $d$，即可得到最终的 Softmax 结果并一次性写回 HBM。
4. **与 FlashAttention 的结合**:
   FlashAttention 正是将这一原理扩展到了 $QK^T$ 的分块乘法和与 $V$ 的乘法中。它不需要在 HBM 中显式写入并读取 $N \times N$ 的注意力矩阵，而是逐块加载 $Q, K, V$，在片上计算局部 $QK^T$，动态进行在线 Softmax 的递推更新，并直接与 $V$ 相乘累加得到输出 $O$。这使得内存访问量从 $O(N^2)$ 骤降到 $O(N)$，彻底攻克了 Attention 的内存带宽瓶颈。
